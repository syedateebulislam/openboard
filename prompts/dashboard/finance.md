Build a rich, mobile-first expense & spend-analytics dashboard tab for this finance dataset that works for any biller, bank, card, or merchant export — never hardcode biller-specific names; infer the useful fields dynamically from the column names and value patterns in the data.

Data model (OpenBoardCLI):
- This dashboard tab loads its real rows at runtime from `useProtectedDashboardData('<dashboard-name>')`. There is NO file upload — the rows are already parsed and served behind authentication. Derive every metric, chart, and table from that hook's rows.
- Dynamically detect the meaningful columns from row keys, case-insensitively: transaction date (date/time/datetime/ordered_at/paid_at/delivered_at/created_at/email_date — prefer the actual transaction/payment date over an email/import date), paid/total amount (amount/paid/total/net/fare/bill/price/charge/subtotal/grand_total/order_total — prefer the final paid amount), discount, tax (tax/gst/vat), fee (fee/charges/platform/delivery/handling/booking/convenience), payment method, currency, merchant/vendor/restaurant/store/service, and description/items.
- Normalize each row into a common internal shape in a `utils/` helper: parse amounts safely (strip currency symbols, commas, spaces), handle negatives/refunds/missing values, parse dates with date-fns across common formats, and never throw on bad input. Mark a row excluded from spend when no valid amount or date is found, and keep an exclusion reason.

Layout (top to bottom):
- Choose 3-6 non-redundant KPIs from supported candidates such as total spend, transaction count, typical transaction, largest transaction, observed fees/taxes/discounts, top merchant, and normalization coverage. Keep currencies separate and show deltas only for complete comparable periods.
- Apply the evidence-first Top Insights contract from the system prompt. Candidate questions include material period-over-period changes, concentration by category or merchant, unusual transactions, fees as an observed share, duplicates, and weekday patterns. Use only candidates supported by sufficient rows and comparison periods. Call something a saving only when an observed discount, refund, reduction, or measurable alternative exists; never turn a large category into a generic "saving opportunity."
- Choose 1-4 Recharts views from supported candidates such as a period spend trend, merchant/category ranking, payment-method composition, or observed fee/tax/discount comparison. Include a trend and period control only with sufficient date span; do not show both a donut and bar for the same breakdown unless each answers a different question.
- Chart hygiene: give every chart an explicit Recharts margin so nothing clips the card edge; horizontal bar charts need a fixed YAxis width (~140) with long labels truncated via an ellipsis tickFormatter (full label in the tooltip); cap dense time-axis ticks (minTickGap or interval="preserveStartEnd"); format axis numbers compactly (12.4k); never render a pie/donut for a dimension with fewer than 2 meaningful values or one dominated by missing/"Not provided" values.
- Usually include a compact recent-records table when transaction inspection is useful, newest first, with proportionate search/sort/pagination and only helpful normalized fields.
- A compact data-quality panel: total rows, rows included, rows excluded, missing-amount rows, invalid-date rows, duplicate transaction ids, and a short note on which columns were auto-detected as amount/date/merchant/fee/tax/discount/payment so the detection is transparent.

Keep it cohesive with the OpenBoardCLI design system: use the shared utility classes and CSS variables (never hardcoded colors), `var(--chart-N)` for series colors, currency/number/date formatting via Intl and date-fns, and split the work into a main tab component plus small components in `components/` and pure helpers in `utils/`. Do not add new dependencies, do not embed raw rows in source, and do not build any upload UI.
