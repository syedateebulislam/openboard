Build (or rebuild) the master "Overview" tab — the landing dashboard that aggregates data from EVERY registered dashboard in this app. It gives the user one place to see totals and trends across all their apps; per-app detail stays in the individual dashboard tabs.

Data model (OpenBoardCLI):
- Load ALL dashboards' data at runtime from `useAllDashboardsData()` from `./hooks/useAllDashboardsData` (never `useProtectedDashboardData`). It returns `{ data, loading, error }` where `data.dashboards` is a record keyed by dashboard slug, each value shaped `{ rows, headers?, summary?, generatedAt? }`.
- Normalization is OpenBoardCLI-owned, NOT yours to write. Import it from `../utils/masterOverview` (a shell file synced from the template on every deploy — never author, rewrite, or return it, and never hand-roll date parsing, amount parsing, or column detection anywhere in the master tab):
  - `normalizeDashboards(data.dashboards)` → `NormalizedRecord[]`, one entry per row of EVERY dashboard: `{ app, slug, date: Date | null, amount: number | null, countOnly: boolean }`. It detects each dashboard's date and amount column per slug (schemas DIFFER per dashboard) by sampling values, so a column whose values do not parse is skipped in favour of one that does.
  - `summarizeApps(data.dashboards, records)` → `AppSummary[]`: `{ app, slug, totalSpend, transactions, datedTransactions, lastActivity: Date | null, hasAmount }`.
  - `periodKey(date, period)` / `periodLabel(key, period)` for the Weekly/Monthly/Quarterly buckets, and `parseAmount` / `parseDate` for any one-off cell you still need.
- Treat `date: null` and `amount: null` as normal: records without a date stay out of dated views (trends, period KPIs, last activity) but still count as transactions, and a dashboard with no usable amount column is count-only — exclude it from spend totals and say so on screen (which apps are spend vs count-only).

Layout (top to bottom):
- A row of KPI cards across ALL apps: total spend (all apps), spend in the past 7 days, spend this month, total transactions, most expensive app, and number of connected apps — with deltas vs the previous period where dates allow.
- A REQUIRED "Top Insights" block of exactly 4 cross-app insights (rendered as InsightCard tiles): the top 2 SPENDING insights (tone "spend" — e.g. highest-spend app this month, fastest-growing app spend, an unusual spike) followed by the top 2 SAVING insights (tone "save" — e.g. app where spend dropped most, cheapest alternative among overlapping categories, biggest savings opportunity), each with a title, headline metric, one-line detail, and confidence (high/medium/low).
- A REQUIRED cross-app spend-trend card: total spend across all apps over time with a Weekly / Monthly / Quarterly period toggle (the shared `.segmented` control inside a `.card-header-row`, title left, toggle right), defaulting to Monthly, offering only the periods the combined date range can support, ideally stacked or multi-line by app using `var(--chart-N)` colors with a legend.
- A per-app breakdown: spend by app as a horizontal bar or donut (skip apps without amounts), plus a compact per-app summary table (app, total spend, transactions, last activity date).
- A REQUIRED "Recent Records" `.data-table` at the bottom: the combined normalized records from ALL apps sorted by date DESCENDING (the 10 most recent visible by default) with an "App" column, pagination (10/25/50/100), sorting, and a text search.
- Chart hygiene: explicit Recharts margin on every chart so nothing clips the card edge; horizontal bars need a fixed YAxis width (~140) with an ellipsis tickFormatter; cap dense time-axis ticks; format axis numbers compactly (12.4k); never render a pie/donut with fewer than 2 meaningful slices.

Keep it cohesive with the OpenBoardCLI design system: shared utility classes and CSS variables only (never hardcoded colors), currency/number/date formatting via Intl and date-fns, `.skeleton` placeholders while loading and friendly empty states. Do not add new dependencies, do not embed raw rows in source, and never assume a specific app exists — derive everything from `data.dashboards` at runtime so the master tab keeps working as dashboards are added or removed.
