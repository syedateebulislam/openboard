Build (or rebuild) the master "Overview" tab — the landing dashboard that aggregates data from EVERY registered dashboard in this app. It gives the user one place to see totals and trends across all their apps; per-app detail stays in the individual dashboard tabs.

Data model (OpenBoardCLI):
- Load ALL dashboards' data at runtime from `useAllDashboardsData()` from `../hooks/useAllDashboardsData` (the master file lives in `src/components`; never use `useProtectedDashboardData`). It returns `{ data, loading, error }` where `data.dashboards` is a record keyed by dashboard slug, each value shaped `{ rows, headers?, summary?, generatedAt? }`.
- Normalization is OpenBoardCLI-owned, NOT yours to write. Import it from `../utils/masterOverview` (a shell file synced from the template on every deploy — never author, rewrite, or return it, and never hand-roll date parsing, amount parsing, or column detection anywhere in the master tab):
  - `normalizeDashboards(data.dashboards)` → `NormalizedRecord[]`, one entry per row of EVERY dashboard: `{ app, slug, date: Date | null, amount: number | null, countOnly: boolean }`. It detects each dashboard's date and amount column per slug (schemas DIFFER per dashboard) by sampling values, so a column whose values do not parse is skipped in favour of one that does.
  - `summarizeApps(data.dashboards, records)` → `AppSummary[]`: `{ app, slug, totalSpend, transactions, datedTransactions, lastActivity: Date | null, hasAmount }`.
  - `periodKey(date, period)` / `periodLabel(key, period)` for the Weekly/Monthly/Quarterly buckets, and `parseAmount` / `parseDate` for any one-off cell you still need.
- Treat `date: null` and `amount: null` as normal: records without a date stay out of dated views (trends, period KPIs, last activity) but still count as transactions, and a dashboard with no usable amount column is count-only — exclude it from spend totals and say so on screen (which apps are spend vs count-only).

Layout (top to bottom):
- Choose a compact KPI row across all apps from metrics the normalized records can support, such as tracked spend, recent-period spend, transaction/activity count, largest spend-bearing app, connected apps, and coverage. Do not show a delta without two complete comparable periods, do not label partial-period movement as growth, and do not repeat the same total under different names.
- Apply the evidence-first Top Insights contract from the system prompt. Select 2-5 material cross-app findings, or fewer when the combined data cannot support them. Candidate questions include concentration, complete-period change, an unusual bucket with its contributing app, recency gaps, and normalization coverage. Never infer that apps are alternatives, call a decrease a saving, or recommend switching/cancelling from unrelated dashboards. Do not compare count-only apps with spend-bearing apps as money.
- When comparable spend exists, render the cross-app period trend as a STACKED `BarChart`, because invoice/order spend is discrete per bucket. Never use smoothed Line/Area curves, `type="monotone"`, or connect values across missing periods. Build one sorted row per period key, initialize every spend-bearing app to numeric zero in every row, then add its amounts; this prevents undefined series, broken segments, and false interpolation. Use `periodKey`/`periodLabel`, a legend and tooltip, compact Y-axis values, `minTickGap`/`interval="preserveStartEnd"`, and an explicit chart margin. Default to Monthly; offer Weekly/Quarterly only when span and density make them readable. Keep all valid buckets visible and let Recharts reduce ticks rather than dropping data.
- Before any cross-app spend total or chart, inspect explicit currency fields in the source rows. If more than one meaningful currency exists, never sum them: group totals/trends by currency when that remains readable, otherwise replace the combined spend visual with per-app/currency summaries and a clear comparability note. Exclude count-only and invalid-amount rows from spend while retaining them in activity counts. If no comparable spend remains, show a useful activity-by-app trend or ranking instead of an empty/garbage money chart.
- A per-app breakdown: spend by app as a horizontal bar or donut (skip apps without amounts), plus a compact per-app summary table (app, total spend, transactions, last activity date).
- Usually include a compact "Recent Records" table at the bottom when record inspection adds value: combined normalized records sorted by date descending, with App, pagination, sorting, and search. Keep undated/count-only rows discoverable without presenting them as spend.
- Chart hygiene: explicit Recharts margin on every chart so nothing clips the card edge; horizontal bars need a fixed YAxis width (~140) with an ellipsis tickFormatter; cap dense time-axis ticks; format axis numbers compactly (12.4k); never render a pie/donut with fewer than 2 meaningful slices.

Keep it cohesive with the OpenBoardCLI design system: shared utility classes and CSS variables only (never hardcoded colors), currency/number/date formatting via Intl and date-fns, `.skeleton` placeholders while loading and friendly empty states. Do not add new dependencies, do not embed raw rows in source, and never assume a specific app exists — derive everything from `data.dashboards` at runtime so the master tab keeps working as dashboards are added or removed.
